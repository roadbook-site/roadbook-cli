# `roadbook-explorer` 与脚手架测试反馈报告

在本次针对 12306 网站的车票查询自动化探索中，我们对 `roadbook-explorer` 技能（Skill）的能力以及 `roadbook init` 生成的脚手架逻辑进行了完整的测试。以下是整个过程中的问题回顾、痛点总结以及改进建议。

## 一、 脚手架 (Scaffold / CLI) 反馈

1. **终端提示信息冗长且乱码**
   - **问题**：`script.py` 顶部的 `print_scaffold_warning()` 函数使用了复杂的 ASCII 字符边框（如 `╔`, `═`, `║` 等）。在部分终端（如 Windows 默认的 PowerShell / CMD 或编码未设置为 UTF-8 的环境）中，这些特殊字符会显示为乱码（Mojibake）。此外，提示文本占用行数过多，干扰了正常的日志查看。
   - **改进**：建议使用简单的 `-` 或 `=` 等基础 ASCII 字符来画线，并精简提示文本，使其紧凑、干净。

2. **最终结果输出刷屏 (未做截断处理)**
   - **问题**：主入口的 `main()` 函数中直接调用了 `print(json.dumps(result))`。当我们的脚本提取了大量的结构化数据（例如 12306 查出的几十趟车次及其所有维度的余票信息）时，会导致终端被巨量的 JSON 字符串刷屏，严重影响用户体验和对关键日志的观察。
   - **改进**：脚手架生成的模板中，应该加入对输出长度的判断。如果 `result` 的 JSON 字符串长度超过一定阈值（例如 200 字符），则进行截断并提示“结果已截断，请查看输出文件”。

## 二、 网站探索与脚本生成 (Skill) 经验与痛点

12306 是一个具有高度自定义 UI 控件的网站，在探索过程中暴露出常规自动化策略的一些局限性：

1. **复杂前端组件的交互困难 (联想输入框)**
   - **痛点**：最初我们尝试使用常规的 `locator.click()` 加上 `keyboard.type('北京')` 来输入出发地和目的地，但这无法稳定触发 12306 网站内部的下拉联想逻辑，最终导致定位下一步元素时抛出 `TimeoutError`。
   - **解决方案**：最终放弃了模拟用户按键，转而使用 `page.evaluate()` 注入 JavaScript，直接解析网页的全局变量 `station_names`（里面包含了车站中文和电报码的映射），并强制修改隐藏表单 `#fromStation` 和显示表单 `#fromStationText` 的值。
   - **对 Skill 的启示**：在面对老旧或防爬严格的国内系统时，模拟按键往往脆弱。Skill 在遇到 `type` 操作反复失败时，应具备“**逆向分析页面 JS 变量和隐藏 DOM 结构**”的意识，考虑直接通过执行 JS 完成赋值。

2. **`readonly` 属性拦截**
   - **痛点**：日期输入框 (`#train_date`) 默认带有 `readonly` 属性（为了强制用户点击日历控件选择）。这会导致 Playwright 的 `.fill()` 报错。
   - **解决方案**：执行 `page.evaluate("document.querySelector('input#train_date').removeAttribute('readonly');")`。
   - **对 Skill 的启示**：Skill 在探测到目标 `input` 元素不可写时，应该自动识别是否存在 `readonly` 属性，并主动生成移除该属性的代码，再进行 `.fill()`。

3. **选择器精度与严格模式 (Strict Mode Violation)**
   - **痛点**：使用 `page.locator("#train_date")` 时，Playwright 报错 `resolved to 2 elements`。因为 12306 页面中存在隐藏的同名 ID 元素。
   - **解决方案**：将选择器升级为 `input#train_date` 解决冲突。
   - **对 Skill 的启示**：探索过程中生成的选择器应该尽量具体，或者在提取 DOM 时如果发现重复的 ID（虽然这不符合 W3C 规范但现实中很常见），应优先使用 `.first` 过滤或加上标签名前缀。

4. **微测试 (Micro-testing) 模式的价值**
   - **经验**：本次任务中，我们没有一上来就在 `script.py` 的庞大框架里死磕，而是先在 `tests/test_12306_search.py` 中编写了一个极其精简的 Playwright 脚本，用于试错并验证上述的 JS 注入策略。跑通之后再将逻辑迁移到主脚本。这证明了脚手架中包含 `tests/` 目录的设计是非常英明的。
   - **对 Skill 的启示**：Skill 应该更主动地利用微测试策略。当遇到复杂的表单提交流程时，先写个几十行的 test 脚本验证走通核心流程，再重构回 `run()` 方法中，效率远高于在主脚本里反复报错。

## 三、 总结

`roadbook-explorer` 结合脚手架提供了一套非常完善的“探索-记录-实现-交付”的工作流。主要优化方向应集中在**提升生成的 CLI 模板对不同终端的兼容性**，以及**增强 AI 面对复杂 DOM 控件（只读属性、自研联想组件、隐藏 ID）时的抗挫折能力和降维打击策略（如 JS 注入）**。

当前脚手架中的 `print` 乱码和未截断问题已在当前的 `script.py` 中进行了修复。
