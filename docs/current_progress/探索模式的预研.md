
# 路书项目 MVP (最小可行性产品) 设计文档

## 1. MVP 目标与边界 (Scope)

**核心目标**：验证“基于语义路标和 CDP 控制的非刚性自动化”是否可行。
**包含 (In Scope)**：
1. **探索模式 (Explore)**：通过 CLI 启动浏览器，获取精简 DOM（带 `@e1` 标记），允许单步执行并记录关键“路标”。
2. **复用模式 (Run)**：读取本地路书文件（YAML），根据“路标”在当前页面寻找目标并执行动作。
3. **异常挂起 (Pause & Intervene)**：当路标找不到时，不直接崩溃，而是暂停执行，等待人工或 Agent 介入（单步调试）。

**不包含 (Out of Scope - 留给 V2)**：
1. 复杂的循环 (Loop) 和条件分支 (If/Else) 语法。
2. 远程路书仓库同步（云端大本营）。
3. 纯视觉多模态大模型（VLM）接入（MVP 阶段先依赖 DOM 文本和属性进行语义匹配）。

## 2. 核心架构精简版 (MVP Architecture)

MVP 采用极简的 **纯 CLI** 架构，底层直接通过 Subprocess 调用 `agent-browser`（由其自带的 Daemon 维持浏览器状态）。

```text
[ Agent / 开发者 ]
       │ (CLI 命令)
       ▼
[ Roadbook CLI ] ──(读写)──> [ 本地路书仓库 (Local YAMLs) ]
       │ (Subprocess 调用 agent-browser CLI)
       ▼
[ agent-browser CLI ]  <-- 解决你的问题1：爬虫与浏览器的沟通枢纽
       │ (IPC 通信)
       ▼
[ agent-browser Daemon ] <-- 维持浏览器 Session、处理 Refs 映射
       │ (CDP 协议 - WebSocket)
       ▼
[ Chrome 浏览器 ]
```

## 3. 核心流程设计 (Core Workflows)

### 3.1 探索与录制流程 (Explore Mode)

解决“如何打开浏览器并记录路书”的问题。探索阶段的核心机制是**“饱和式记录 (Saturated Recording)” + “提纯 (Distill)” + “Stage 驱动”**。

1. **初始化会话与高频观察**：`roadbook explore github_login "https://github.com/login"`
    - _设计考量_：启动时必须赋予一个会话名称（如 `github_login`），底层会在 `~/.roadbook/sessions/` 创建一个临时工作区。
    - _底层动作_：启动 Chrome，建立 CDP 连接。后台 Daemon 开始以 **0.5秒为周期** 进行 DOM 快照，开启**饱和式记录**（记录所有快照、鼠标轨迹、试错动作）。
2. **反复探索与试错**：
    - 开发者或 Agent 开始单步试探（`roadbook step ...`）。
    - 所有的误操作、回溯、页面加载等待，都会被完整记录在 Raw Buffer（原始缓冲）中。
3. **人类介入 (Human Intervention) 与无限期挂起**：
    - 遇到复杂场景（如输入密码、过图形验证码），CLI 触发挂起状态（无 Timeout）。
    - 人类在真实浏览器中完成操作后，在终端输入 `roadbook continue`，系统恢复自动录制，并根据前后的 DOM 快照 Diff 自动推断出人类干预的结果。
4. **阶段划分与提纯 (Stage & Flush)**：`roadbook stage "到达登录页"`
    - _设计考量_：这是核心的**清洗动作**。
    - _底层动作_：触发 `Flush` 机制，将 Raw Buffer 中的冗余快照、被回溯的无效动作（如点错了又退回来的步骤）**清理掉**，只提取出当前 Stage 的“有效主线路径”，压入内存中的 Roadbook AST（抽象语法树）。
5. **保存路书**：`roadbook save`
    - _底层动作_：将内存中已经过 Stage 提纯的 AST 序列化为最终的 YAML 文件。

### 3.2 路书复用与执行流程 (Run Mode)

解决“探索之后如何复用”的问题。

1. **加载路书**：`roadbook run github_login.yaml`
2. **环境校验 (Pre-condition Check)**：
    - 在进入每一个 Stage 之前，或者在**人类介入（长时挂起）恢复后**，系统会首先执行环境校验（如检查当前 URL、或寻找特定标志物）。
    - 如果环境被意外篡改，CLI 会触发异常挂起，提示：“环境状态与预期不符，请检查浏览器”。
3. **寻找路标 (核心逻辑)**：
    - 读取当前 Step：意图是“输入用户名”，特征是“Username”。
    - 调用 `agent-browser` 实时拉取当前页面的精简 DOM。
    - **模糊匹配**：在当前 DOM 中寻找 label 或 placeholder 包含 "Username" 的输入框。
4. **执行动作**：找到目标后，转换为底层的 `@eXX` ID，通过 CDP 执行 `type`。
5. **容错与挂起 (解决你的问题3)**：
    - 如果页面改版，找不到 "Username" 怎么办？
    - **MVP 策略**：触发 `Breakpoint`。CLI 返回 `Status: Paused. Target "Username" not found.`
    - Agent 此时可以调用 `roadbook inspect` 重新观察，发现变成了 "Email address"，然后调用 `roadbook step` 手动执行，并选择是否 `patch` 修复路书。

## 4. 数据结构设计 (Roadbook YAML)

路书不是简单的线性代码，而是一份经过**提纯（Distilled）**，包含等待机制、人类介入、环境校验和 Stage 的“探险攻略”。（注：原始的试错记录保存在 session 的 raw_log 中，不污染最终的 YAML）。

```yaml
# ~/.roadbook/library/github_login.yaml
name: github_login
description: "GitHub 登录标准流程"
version: 1.0

stages:
  - name: "阶段一：打开并加载登录页"
    # 新增：前置环境校验，确保执行起点的正确性
    pre_condition:
      url_contains: "github.com"
    steps:
      - id: s1_s1 # 采用程序自动生成的结构化 ID (首字母缩写)，清晰且易于解析
        intent: "打开登录页面"
        action: "goto"
        value: "https://github.com/login"
      - id: s1_s2
        intent: "等待页面网络请求停止"
        action: "wait"
        condition: "networkIdle"

  - name: "阶段二：输入账号与人工验证"
    pre_condition:
      landmark: { role: "textbox", keyword: "Username or email" }
    steps:
      - id: s2_s1
        intent: "定位用户名输入框并输入"
        action: "type"
        landmark: { role: "textbox", keyword: "Username or email" }
        value: "${GITHUB_USER}"
        
      # 新增：Checkpoint 作为一种特殊的 Step，用于记录执行轨迹、截图和耗时，方便事后核对与排错
      - id: s2_s2
        type: "checkpoint"
        intent: "记录点击登录按钮后的页面状态"
        location_desc: "登录提交后的过渡页面或结果页面" # 语义化的位置描述
        url_pattern: "github.com/login|github.com/session" # URL 模式匹配
        snapshot: true             # 强制截图并保存 DOM 快照
        metrics:
          author_time_spent: 1500  # 录制者在此处停留/耗时的毫秒数，供执行时参考或统计
        
      - id: s2_s3
        intent: "等待人类输入密码并处理验证码"
        action: "wait_for_human"
        prompt: "请在浏览器中输入密码，通过验证码后在终端输入 roadbook continue"
      - id: s2_s4
        intent: "观察到页面发生跳转，等待新页面稳定"
        action: "wait"
        condition: "dom_stable"

  - name: "阶段三：验证结果"
    # 新增：人类介入后，或者长时等待后，必须先校验环境状态是否符合预期
    pre_condition:
      url_contains: "github.com/dashboard"
    steps:
      - id: s3_s1
        intent: "验证是否登录成功"
        action: "verify"
        landmark: { keyword: "Dashboard" }
```

## 5. 针对你提出的三个问题的解答与设计映射

### 问题 1：爬虫是怎么跟浏览器沟通的？它从浏览器获得什么？
* **沟通机制**：在 MVP 中，Roadbook CLI 通过 Subprocess 调用 `agent-browser` CLI，由底层的 `agent-browser Daemon` 通过 **CDP (Chrome DevTools Protocol)** 与浏览器建立 WebSocket 连接并执行动作。
* **获得什么**：
  1. **DOM 树与无障碍树 (Accessibility Tree)**：用于提取页面上有意义的交互元素（按钮、链接、输入框），过滤掉无用的 `<div>` 包装。
  2. **坐标与可见性**：获取元素的真实屏幕坐标，用于模拟真实的鼠标点击（规避反爬）。
  3. **网络与控制台事件**：监听 Network 请求（判断页面是否加载完）和 Console 报错。

### 问题 2：本地仓库、远程仓库怎么管？
* **MVP 阶段（本地仓库）**：
  * 所有的路书就是一个个 `.yaml` 文件，统一存放在 `~/.roadbook/library/` 目录下。
  * `roadbook search` 命令本质上就是在这个目录下做全文检索（grep）。
* **未来演进（远程仓库）**：
  * 引入 Git 机制。路书本质是文本，非常适合用 Git 进行版本控制。
  * 远程仓库就是一个 GitHub Repo，大家可以通过 `roadbook pull <repo_url>` 共享“探险攻略”。

### 问题 3：路书里的循环、分叉、可选不可选怎么处理？
* **设计哲学：路书是攻略，不是强类型代码。**
* **MVP 解法（线性 + 挂起）**：
  * MVP 不做复杂的 `if/else` 语法。路书只记录“主线任务（Happy Path）”。
  * 如果遇到“可选”的弹窗（比如偶尔弹出的“是否开启通知”），路书在寻找该路标时如果设置了 `optional: true`，找不到就直接跳过。
  * 如果遇到“分叉”（比如有时需要图形验证码，有时不需要），主线路书会因为找不到下一个路标而**挂起（Paused）**。此时控制权交还给 Agent（探险家），Agent 通过 `inspect` 发现当前是验证码页面，调用专门处理验证码的 Skill/Sub-roadbook，处理完后再让主线 `run --resume` 继续。
  * **总结**：把复杂的决策逻辑交给外层的 Agent，路书只负责提供“路标”和“执行确定性动作”。
