# 路书项目阶段性目标 (Milestone Objectives)

## 核心演进逻辑
路书 MVP 的实现将遵循**“渐进式自动化”**的原则。从完全依赖大模型（Agent）的泛化理解能力开始，逐步过渡到“程序主导执行 + Agent兜底异常”的半自动化模式。

---

## 阶段一：探索与验证期 (Agent as the Engine)

**定位**：用最“笨”但也最灵活的办法，跑通核心闭环。
**核心机制**：没有解析程序，没有严苛的语法规范。路书是写给 Agent 看的“操作样例”。Agent 作为连接路书和网页的唯一中枢，边看路书边调用浏览器控制工具执行。

### 阶段目标
1. **验证模式可行性**：验证 Agent 是否能理解自然语言/半结构化的路书，并准确转化为浏览器操作。
2. **沉淀最佳实践**：通过大量测试（如各种网站的登录场景），观察 Agent 在遇到障碍时是如何思考和解决的。
3. **制定初步规范**：从无意识的试错中，总结出哪些“路标描述”（如 XPath、CSS、语义标签）最稳定，提炼出路书的初代模板。

### 交付产出 (Deliverables)
- [ ] **基础工具链**：一套能让 Agent 顺利控制浏览器（点击、输入、导航、获取DOM快照）的底层工具。
  - **当前进展**：已初步建立 `roadbook-stepper` (路书单步执行器) Skill。这是目前第一阶段的核心引擎，后续各项探索任务将主要围绕该 Skill 来推进，利用它指导 Agent 严格按照路书结构一步步解析与执行网页操作。
- [ ] **高频场景样例库 (Sample Library)**：3-5 个用自然语言或拟代码编写的典型路书样例（如 `github_login_sample.md`）。
- [ ] **异常处理经验库 (Experience Log)**：记录 Agent 曾遇到的坑及解决对策（如：如何处理动态加载、如何应对非预期弹窗）。

---

## 阶段二：提效与半自动化期 (Program + Agent in the Loop)

**定位**：将确定的步骤交给程序，将不确定的异常交给 Agent。
**核心机制**：引入专用的 **Roadbook Runner (执行器程序)**。常态下，Runner 以极高的效率解析结构化路书并自动执行。当 Runner 遇到无法跨越的障碍（如元素丢失、页面改版、出现验证码）时，触发挂起（Pause），并唤起 Agent 介入处理。

### 阶段目标
1. **构建自动化通道**：编写 CLI 程序，使其能够解析第一阶段沉淀下来的路书规范（如提取为 YAML/JSON），并自动下发指令给浏览器进程。
2. **实现“人机无缝切换”**：理顺 Agent 的“介入与交还”机制。Agent 解决完当前阻碍后，能让 Runner 继续顺着路书往下跑。
3. **提升执行效率**：将单次跑通路书的耗时和 Token 成本大幅降低。

### 交付产出 (Deliverables)
- [ ] **Roadbook Runner (MVP 引擎)**：一个轻量级的 Python/Node.js 脚本或 CLI 工具，支持 `roadbook run <name.yaml>`。
- [ ] **结构化路书规范 (Schema)**：基于第一阶段经验，制定出的路书数据结构规范（如 YAML Schema），定义 intent, action, pre_condition 等标准化字段。
- [ ] **断点与接管机制设计**：Runner 能够抛出标准化的错误上下文（当前DOM快照、截屏、报错节点），以便 Agent 迅速理解现状并接管。

---

## 阶段三：自我修复与进化 (Self-Healing) - [未来展望]

**定位**：让路书具备生命力，自动适应网页变化。
**核心机制**：当 Runner 失败、Agent 介入并成功解决问题后，Agent 不仅能让当前流程继续，还能**自动回写和修补 (Patch)** 原始路书文件，更新失效的路标。

### 阶段目标
1. 实现路书的“阅后即焚”与“动态热更”。
2. **产出**：路书自动修复工具 / 动态路书仓库。
